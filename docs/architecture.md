# Architecture

## Components

The demonstration has four independently meaningful components:

1. The researcher web application collects a report and invokes the local C++ client. It
   never interprets CBOR or performs cryptographic operations.
2. The C++ client builds and signs the SD-CWT, manages disclosures and proof bundles,
   and performs verification. It uses CCF crypto and CCF's EverCBOR-backed `ccf::cbor`
   implementation.
3. The pinned `scitt-ccf-ledger` submodule runs an unmodified SCITT transparency
   service.
4. The mock MSRC service stores the full proof bundle and creates reduced presentations
   by asking the C++ client to remove disclosures.

The Python applications move `.cose`, `.cbor`, certificate, and key files as opaque
bytes. They do not depend on `cbor2`, `pycose`, or `pyscitt`.

## Submission protocol

The researcher application performs this ordered transaction:

1. Derive the public key from the researcher-controlled private key through the C++
   client.
2. Send only that public key to the mock MSRC enrollment endpoint.
3. Receive a short-lived leaf certificate chaining to the MSRC root.
4. Ask the C++ client to create an X.509-signed SD-CWT with no disclosures in its
   unprotected header.
5. Submit those exact bytes to SCITT.
6. Wait until SCITT returns a transparent statement with an embedded receipt.
7. Ask the C++ client to create a proof bundle containing the exact registered
   statement, transparent statement, and all disclosures.
8. Send that bundle to MSRC.

The UI has one Submit action. A failure in step 8 does not erase the successful SCITT
registration: the researcher can download the bundle and retry delivery.

## Signed statement profile

The COSE Sign1 protected header contains:

| Label | Meaning                                                |
| ----- | ------------------------------------------------------ |
| `1`   | ECDSA algorithm selected by the CCF key implementation |
| `2`   | Critical labels `[15, 33]`                             |
| `15`  | CWT issuer and subject used by the SCITT X.509 profile |
| `16`  | `293`, the SD-CWT media type                           |
| `33`  | DER X.509 chain ordered leaf to root                   |
| `170` | SD-CWT disclosure hash algorithm                       |

All report content is represented by redacted hashes in the signed payload. Salts are
generated by CCF's cryptographically secure entropy source.

The SCITT receipt is placed in unprotected header `394`. Disclosures are placed in
unprotected header `17`. Neither changes the researcher's signature. The proof bundle
retains the exact registered bytes because SCITT registration is defined over those
bytes.

## Text disclosure

The report body is split at a source constant of six Unicode code points. The chunks are
stored in a map keyed by stable integer index. A presentation that reveals selected
chunks includes the body-parent disclosure and only the selected child disclosures. A
map avoids the index shifting that occurs when undisclosed SD-CWT array elements are
omitted.

Changing the chunk size is a source-level profile change and requires recompilation and
a profile-version update.

## Verification

Verification produces separate results for:

- MSRC root trust, leaf validity, certificate chain, and the `did:x509` certificate
  policy (subject in this demo, or EKU when configured);
- consistency of the `did:x509` issuer with the trusted root;
- researcher COSE signature;
- disclosure hashes and selected content;
- equality of the protected header, payload, and signature between the exact registered
  and transparent statements;
- SCITT receipt validity against separately supplied SCITT trust material.

No result is inferred from another. In particular, a valid SCITT receipt proves
registration and ordering, not the truth of the report or semantic equivalence between
two vulnerabilities.
